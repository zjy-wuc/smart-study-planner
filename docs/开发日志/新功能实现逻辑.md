业务逻辑：
先从provider层讲，这个文件是专门负责项目与api沟通的。我们直接讲解核心函数async def stream_completion  负责把其他service的message传递给大模型并且接受结果
首先传经来massage，然后组装成payload，异步发送给大模型，然后等待请求返回。但是我们的是流式输出，所以返回的结果是一条条而且多次返回，所以我们的这个函数的返回体是AsyncGenerator，支持多次返回。这个函数的核心就是async for line in response.aiter_lines()，
一行行多次读取数据，按结构依次检查data，choices，delta，content捕获我们的文本，然后yield出去期间每次转换都会有一个if检查，最后还有个统一的错误处理超时错误和httpx错误



其次是并发额度限制与状态结算
guard_service
核心的函数有2个
admit_request：首先，用户进入函数先发一把事务锁，然后开始检查，看token是否够量，是否有多个请求再运行，不通过就打回，通过就数据入库，状态改为running，然后返回admission，然后commit释放锁

其次就是metered_ai_stream
我们之前有了状态写入函数，那么就有状态完成函数。这个函数针对我们的stream流。首先，函数需要传入admission和事件包，然后开始一行行遍历数据。如果不是最终状态done", "blocked", "error"，就yield再continue，是的话先更新数据库状态，然后再yield。期间有很多的检查，例如格式是否正确，最后也有统一的错误raise

最后是service，这个就负责对信息的检查与审核了
这里我们主要提供两个审查函数_contains_credentials 这给函数利用正则表达式直接把文本关于密钥的信息匹配，从而进行筛选，只能筛选完整文本，很乏味
所以这里实现了流式输出的升级版用 stream_checked_completion
在返回流式结果是还会检查数据接下来是实现逻辑
流式返回数据就不多讲了，我们主讲对于返回数据的检查
对于返回的数据，我们的核心思想是设置缓冲区pending，然后挨个检查。对于返回的数据，先检查字数是否超了，然后把数据加到缓冲区，然后只要缓冲区的长度大于一次递出去的量+要检查留在缓冲区量，我们就用变量review来接收检查尾和缓冲区的部分数据，们问题后，我们就更新缓冲区，检查尾巴（加上数据-留在缓冲区的量），最后yield text，最后，如果有少量缓存残留，那么直接yield出去并且yield完成事件
