# 1. 项目建设背景

## 1.1 原有认证系统

Auth V1.0 已经具备：

- 用户名密码注册。
    
- 用户名密码登录。
    
- JWT 双 Token。
    
- Access Token 自动续期。
    
- Refresh Token 轮换。
    
- Refresh Token 重放检测。
    
- 当前会话退出。
    
- 全部会话退出。
    

但是原有系统仍然存在一些不足：

|原有问题|带来的影响|
|---|---|
|不支持邮箱验证|无法验证邮箱所有权|
|不支持忘记密码|缺少账号找回机制|
|Access Token 无法即时撤销|用户退出后旧 Access 仍可能有效|
|缺少独立会话表|无法完整管理登录设备|
|双 Token 保存在 localStorage|Refresh Token 存在被前端脚本读取的风险|
|缺少登录失败限制|无法有效限制密码猜测|
|缺少验证码限流|邮件服务可能被滥用|
|缺少认证日志|难以追踪关键安全事件|
|认证 SQL 集中在 Service|分层职责不够清晰|
|缺少过期数据清理|历史认证记录持续增长|

Auth V2.0 的目的不是简单增加几个登录页面，而是将基础登录系统升级为具备完整生命周期管理能力的账号认证系统。

## 1.2 本次升级目标

实现以下完整业务闭环：

注册 → 邮箱验证 → 登录 → 身份认证 → Token 刷新 → 会话管理 → 账号安全变更 → 会话撤销 → 历史数据清理。

同时满足：

- 安全性。
    
- 数据一致性。
    
- 并发正确性。
    
- 可维护性。
    
- 低资源部署。
    
- 原有学习业务兼容性。

# 3. 整体技术架构

## 3.1 分层架构

```
前端 HTTP 请求
        │
        ▼
FastAPI Router
        │
        ├── Pydantic 参数校验
        ├── Depends 依赖注入
        └── Cookie / Origin 安全检查
        │
        ▼
Service 业务层
        │
        ├── 身份认证
        ├── Session 管理
        ├── 邮箱验证码
        ├── 账号安全
        ├── 限流与事务控制
        └── 头像管理
        │
        ▼
Repository 数据访问层
        │
        └── SQLAlchemy Session + text()
        │
        ▼
MySQL
```

本项目继续采用原生 SQL，而不是引入 ORM Models 和 Alembic。

通过 SQLAlchemy 提供数据库连接管理、参数绑定和事务管理能力。

## 3.2 各层职责

### Router

负责：

- 接收 HTTP 请求。
    
- 参数校验。
    
- 调用身份认证依赖。
    
- 调用 Service。
    
- 设置或删除 Cookie。
    
- 构造统一响应。
    

Router 不直接编写认证业务 SQL。

### Service

负责：

- 判断业务规则。
    
- 组织多个 Repository。
    
- 权限校验。
    
- 管理事务。
    
- 控制并发。
    
- 处理异常。
    
- 保证业务一致性。
    

Service 是整个认证系统最重要的一层。

### Repository

负责：

- 执行 SQL。
    
- 查询数据。
    
- 更新数据。
    
- 返回执行结果。
    
- 根据需要使用 `FOR UPDATE`。
    

Repository 不主动调用 `commit()` 或 `rollback()`。

原因是 Repository 无法判断整个业务是否已经执行完成。事务必须由最了解业务全貌的 Service 控制。

# 4. A0：数据库设计与迁移

## 4.1 最少建表原则

本次没有为了每一个认证功能分别创建数据库表。

新增三张表：

- `login_sessions`
    
- `email_verifications`
    
- `auth_events`
    

修改已有的 `users`，并将原来的 `tb_refresh_token` 重命名为 `refresh_tokens`。

最终认证模块主要使用五张表。

## 4.2 数据表职责

|数据表|职责|
|---|---|
|users|用户账号与个人资料|
|login_sessions|登录会话生命周期|
|refresh_tokens|Refresh Token 摘要与轮换历史|
|email_verifications|邮箱验证码及发送、消费状态|
|auth_events|认证准入、安全事件和失败计数|

## 4.3 数据关系

```
users
  │
  ├── 1:N login_sessions
  │         │
  │         └── 1:N refresh_tokens
  │
  ├── 逻辑关联 email_verifications
  │
  └── 逻辑关联 auth_events
```

注意：Session 与 Refresh Token 通过 `user_id + family_id` 进行逻辑关联，并非所有关系都建立物理外键。

因此 Service 必须承担相应的数据一致性保障责任。

## 4.4 users 表关键字段

|字段|用途|
|---|---|
|id|用户唯一标识|
|username|用户名|
|password_hash|密码摘要|
|password_updated_at|最近密码更新时间|
|email|唯一绑定邮箱|
|email_verified_at|当前邮箱验证时间|
|nickname|昵称|
|avatar_url|头像访问路径|
|is_active|账号是否启用|

其中 `password_updated_at` 和 `email_verified_at` 不仅用于记录时间，还可以作为判断旧验证码是否失效的安全边界。

## 4.5 数据库迁移经验

本次使用隔离数据库 `ssp_a0_migrate2` 进行开发与测试。

正式迁移前需要：

1. 完整备份。
    
2. 验证备份可以恢复。
    
3. 核对表结构及外键。
    
4. 停止旧版写入程序。
    
5. 按依赖关系清理旧数据。
    
6. 执行结构迁移。
    
7. 校验表、索引和数据状态。
    
8. 与新版前后端协调上线。
    

必须理解 MySQL DML 与 DDL 的区别。

DELETE、UPDATE、INSERT 等事务性 DML 可以在事务中回滚。

ALTER TABLE、CREATE TABLE、RENAME TABLE 等 DDL 通常涉及隐式提交，不能简单假设整个迁移脚本能够统一回滚。

因此数据库迁移需要分阶段检查，而不是遇到错误后直接重跑整个脚本。

正式数据库尚未迁移。

# 5. 密码安全与密码哈希

## 5.1 为什么密码不能明文保存？

如果数据库泄露，明文密码会直接暴露用户凭证。

因此系统只保存密码哈希，不保存原始密码。

本项目使用：

```
PBKDF2-HMAC-SHA256
迭代次数：600000
随机盐：16 字节
摘要长度：32 字节
```

存储格式：

```
算法$迭代次数$随机盐十六进制$密码摘要十六进制
```

## 5.2 PBKDF2 的作用

普通 SHA256 计算速度非常快，不适合作为直接的密码存储算法。

PBKDF2 通过大量重复计算，提高每次密码猜测的成本。

随机盐能够避免两个用户使用相同密码时产生完全相同的存储摘要。

注意：

- 哈希不是加密。
    
- 密码哈希不需要解密。
    
- 盐不需要保密。
    
- 迭代次数并不意味着密码绝对安全。
    

## 5.3 密码验证流程

```
读取数据库中的密码摘要
        ↓
解析算法、迭代次数、盐和摘要
        ↓
使用用户输入密码重新计算
        ↓
hmac.compare_digest()
        ↓
判断是否匹配
```

源码位置：

`app/core/security.py`

核心函数：

- `hash_password()`
    
- `verify_password()`
    

本次还增加了非法摘要类型、迭代次数、盐长度和摘要长度的检查，避免异常数据库数据直接导致服务器500错误。

# 6. JWT + Session 混合认证

这是本次升级最重要的架构变化。

## 6.1 JWT 的职责

JWT 是一种携带声明并通过签名验证的凭证格式。

本项目 Token 中主要包含：

|声明|含义|
|---|---|
|sub|用户 ID|
|family_id|登录会话 ID|
|iat|签发时间|
|exp|过期时间|
|type|access 或 refresh|
|jti|Token 唯一标识|

JWT 可以证明凭证由可信服务端签发，并且没有被非法篡改。

但 JWT 并不会自动证明用户当前仍处于允许登录的状态。

## 6.2 Session 的职责

`login_sessions` 表记录：

- 会话标识。
    
- 所属用户。
    
- User-Agent。
    
- 登录时间。
    
- 最近活跃时间。
    
- 绝对过期时间。
    
- 撤销时间。
    
- 撤销原因。
    

因此：

JWT 负责验证凭证是否合法。

Session 负责验证这份凭证当前是否仍然被系统认可。

## 6.3 双 Token 与 Session 有效期

|项目|默认期限|
|---|---|
|Access Token|15分钟|
|Refresh Token|7天|
|Session 空闲期限|7天|
|Session 绝对期限|30天|
|活跃时间写入间隔|300秒|

这些期限不是简单叠加关系。

即使 Refresh Token 尚未过期，只要 Session 已被撤销、空闲过期或绝对过期，也不能继续刷新。

Refresh Token 签发时不能超过 Session 的绝对有效期限。

## 6.4 family_id 的作用

`family_id` 使用 UUID4。

每次成功登录创建一个新的 family_id。

同一次登录产生的：

- Access Token。
    
- Refresh Token。
    
- 后续轮换生成的 Refresh Token。
    
- Session 数据库记录。
    

都关联同一个 family_id。

例如：

```
用户 1001
  │
  ├── 电脑 Session A
  │     ├── Access A
  │     ├── Refresh A1
  │     ├── Refresh A2
  │     └── Refresh A3
  │
  └── 手机 Session B
        ├── Access B
        └── Refresh B1
```

撤销 Session A 不会撤销 Session B。

family_id 表示一次逻辑登录会话，并不是物理设备的唯一硬件标识。

## 6.5 Access Token 即时撤销

新版 `get_current_user()` 的认证流程：

```
提取 Authorization Bearer
        ↓
验证 JWT 签名和必要声明
        ↓
验证 Token 类型与有效期
        ↓
提取 sub 和 family_id
        ↓
联合查询 users 与 login_sessions
        ↓
检查账号状态
        ↓
检查 Session 是否撤销或过期
        ↓
返回当前用户身份
```

核心判断：

```
if session["revoked_at"] is not None:
    reject_auth(
        "SESSION_REVOKED",
        "登录会话已撤销",
    )
```

撤销事务提交后，即使 JWT 仍然符合签名和过期时间要求，也无法通过下一次受保护请求的认证。

这就是所谓的 Access Token 即时撤销。

准确来说，不是 JWT 字符串被删除或者密码学签名失效，而是它失去了服务端授权。

### 即时撤销的边界

已经通过身份认证并开始执行的请求，不保证立即中断。

例如已经建立的 AI SSE 流式请求，当前设计不会自动终止；下一次请求才会再次验证 Session。

## 6.6 与纯 JWT 方案相比的取舍

优点：

- 可以即时撤销会话。
    
- 可以管理多设备登录。
    
- 可以实现远程退出。
    
- 可以统一执行账号安全变更。
    

代价：

- 每次受保护请求需要查询数据库。
    
- 系统不再是完全无状态认证。
    
- 数据库可用性会影响身份验证。
    

本项目采用用户与 Session 联合查询，尽量降低额外数据库访问成本。

# 7. Refresh Token 轮换与重放检测

## 7.1 为什么需要轮换？

如果 Refresh Token 长期不变，一旦泄露，就可能在有效期内被重复使用。

轮换机制要求：

每次使用合法 Refresh Token 刷新时，签发新的 Refresh Token，并使旧 Refresh Token 不再允许正常刷新。

## 7.2 数据库记录

`refresh_tokens` 主要字段：

- token_hash。
    
- user_id。
    
- family_id。
    
- expires_at。
    
- revoked_at。
    
- replaced_by。
    
- created_at。
    

数据库只保存 Refresh Token 的 SHA256 摘要。

Refresh Token 具有较高随机性，与低熵密码不同，因此不需要再执行 PBKDF2。

## 7.3 正常轮换

```
客户端发送 Refresh A1
        ↓
验证 JWT
        ↓
锁定 User
        ↓
锁定 Session A
        ↓
锁定 Refresh A1
        ↓
检查当前记录仍然有效
        ↓
生成 Refresh A2 和新 Access
        ↓
将 A1 标记为已轮换
        ↓
插入 A2 的摘要
        ↓
提交事务
```

旧 Token 的 `replaced_by` 保存下一代 Token 的摘要。

## 7.4 重放检测

假如已经轮换的 Refresh A1 再次被提交，后端无法可靠判断这究竟是恶意重放，还是合法客户端发生了并发刷新。

本项目选择严格重放检测：

```
A1 已被 A2 替换
        ↓
再次收到 A1
        ↓
检测 replaced_by 不为空
        ↓
撤销整个 Session A
        ↓
撤销该 Family 的 Refresh Token
        ↓
提交撤销事务
        ↓
返回 401 SESSION_REVOKED
```

其他登录会话不受影响。

该检测依赖旧 Token 记录仍然存在，并且请求能够通过前置 JWT 校验。已经超过 JWT 有效期的旧 Token 不会进入相同的有效重放检测路径。

## 7.5 为什么先提交再抛异常？

错误写法：

```
with db.begin():
    revoke_session(...)
    raise HTTPException(...)
```

异常会使尚未提交的事务回滚，导致刚刚执行的撤销没有真正生效。

正确的业务要求是：

先持久化撤销结果，再向客户端报告认证失败。

当前实现使用显式提交后抛出异常的方式。

这是本次开发非常重要的事务知识点。

## 7.6 对前端提出的要求

严格重放检测虽然更安全，但要求前端可靠协调刷新请求。

否则两个标签页同时使用同一个旧 Refresh Token，第二个请求可能触发整个会话撤销。

因此前端需要：

- Promise 单飞。
    
- 跨标签页锁。
    
- 登录、刷新、退出之间的协调。
    
- 防止旧异步结果覆盖新认证状态。
    

后端和前端安全机制必须配合设计。

# 8. HttpOnly Cookie、CORS 与 CSRF

## 8.1 新版凭证存储方式

|凭证|客户端存储位置|传输方式|
|---|---|---|
|Access Token|前端运行时内存（待前端落实）|Authorization Header|
|Refresh Token|HttpOnly Cookie|浏览器自动携带|

Refresh Token 不再通过 JSON 响应返回，也不再从请求体读取。

## 8.2 Cookie 安全属性

|属性|作用|
|---|---|
|HttpOnly|禁止 JavaScript 直接读取|
|Secure|生产环境通过 HTTPS 发送|
|SameSite=Lax|限制跨站携带|
|Path=/auth|限制 Cookie 发送路径|
|Max-Age|控制客户端保存期限|
|Host-only|不主动扩大到其他域名|

HttpOnly 可以降低长期凭证被脚本直接窃取的风险，但不能彻底消除 XSS。

恶意脚本仍可能代表当前页面发起请求，因此其他前端安全措施依然重要。

## 8.3 CORS 与 CSRF 的区别

CORS 主要控制浏览器是否允许网页跨源读取响应和执行特定跨源请求。

CSRF 则是利用浏览器可能自动携带身份凭证的行为，在用户不知情的情况下触发状态变更。

两者不是同一个概念。

## 8.4 本项目的防护

对于认证状态变更请求，要求：

- Origin 属于明确白名单。
    
- 存在 `X-CSRF-Protection: 1` 请求头。
    
- CORS 允许的来源与认证白名单保持一致。
    
- 凭证请求不允许任意来源。
    
- 生产环境使用 HTTPS。
    

自定义请求头不是秘密验证码。它的作用是结合浏览器跨源预检机制和严格 Origin 检查，限制非授权网页发起认证请求。

源码位置：

`app/core/auth_cookie.py`

# 9. 邮箱验证码系统

这是本次开发中另一套完整的安全子系统。

## 9.1 五种验证码用途

|Purpose|业务|
|---|---|
|REGISTER|注册|
|LOGIN|邮箱验证码登录|
|RESET_PASSWORD|忘记密码|
|CHANGE_EMAIL_OLD|验证原邮箱|
|CHANGE_EMAIL_NEW|验证新邮箱|

验证码必须与业务用途匹配。

注册验证码不能用于登录，登录验证码不能用于重置密码。

换绑验证码还需要绑定用户及当前 Session，防止其他会话使用。

## 9.2 验证码规则

|规则|默认值|
|---|---|
|验证码长度|6位数字|
|有效期|5分钟|
|重发冷却|60秒|
|单个验证码最大错误次数|5次|
|单邮箱每日额度|10次|
|单IP每日发码额度|30次|
|全站每日额度|本次 .env 已配置240次|
|成功消费|只能一次|

所有限制必须由后端执行。

前端倒计时只是交互提示，不能作为安全保障。

## 9.3 为什么验证码使用 HMAC？

六位数字验证码的取值空间只有100万个。

如果直接保存验证码的普通 SHA256 摘要，数据库泄露后仍可能通过枚举全部候选值进行离线验证。

本项目使用独立的 `EMAIL_CODE_SECRET`，对邮箱、用途、验证码计算 HMAC-SHA256。

```
HMAC(
    服务端独立密钥,
    邮箱 + 用途 + 验证码
)
```

数据库不保存明文验证码。

注意：HMAC 防护依赖服务端密钥保密。在线验证码尝试仍然必须依靠限流和失败次数控制。

## 9.4 验证码状态机

```
生成验证码
    ↓
PENDING
    ↓
调用 Brevo HTTP API
    ├── 服务商接受 → SENT
    └── 发送失败   → FAILED
```

发送状态之外，还独立维护：

- attempts。
    
- expires_at。
    
- consumed_at。
    
- invalidated_at。
    

SENT 表示服务商已接受发送请求，不等于邮件已经到达收件箱。

## 9.5 为什么先入库，再发送？

如果先发送邮件，再写数据库，会出现一种异常情况：

邮件已经成功发出，但数据库写入失败，用户收到的验证码却不能使用。

所以我们采用：

1. 获取全局发码命名锁。
    
2. 检查发送额度。
    
3. 作废旧验证码。
    
4. 写入 PENDING 记录。
    
5. 提交数据库事务。
    
6. 释放命名锁。
    
7. 调用 Brevo。
    
8. 独立事务更新 SENT 或 FAILED。
    

外部 HTTP 请求不放在长数据库事务和额度锁中。

发送失败也不自动退还额度，避免反复失败请求绕过限流。

## 9.6 验证与消费分离

`check_verification()`：

检查验证码是否满足使用条件。

`consume_verification()`：

将正确验证码正式标记为已经使用。

两个函数分离是为了支持复杂事务。

例如邮箱换绑需要旧邮箱码和新邮箱码同时正确。

如果检查旧码后立即消费，而新码错误，就会导致用户无法继续使用原本正确的旧码。

因此两个验证码先完成校验，等邮箱更新等业务全部可以成功时，再统一消费和提交。

## 9.7 安全状态变更后的旧验证码

最新交付代码增加了安全时间边界：

```
valid_after = max(
    user["password_updated_at"],
    user["email_verified_at"],
)
```

验证码创建时间必须晚于该边界。

这样，改密或换绑前签发的 LOGIN、RESET_PASSWORD 和换绑验证码将不能继续使用。

此项整改需要最终回归测试，尤其需要验证发码与账号安全变更并发执行的情况。

仅依靠应用时间戳不应被认为已经严格解决所有事务可见性与多进程时钟问题。如测试发现竞态，需要进一步结合锁或安全版本控制处理。

# 10. MySQL 事务：本次开发的核心难点

## 10.1 什么是事务？

事务是一组需要作为整体执行的数据库操作。

例如注册：

```
插入用户
创建 Session
插入 Refresh Token 摘要
消费验证码
记录认证事件
```

这些操作应该全部成功，或者全部失败。

不能允许注册成功却没有会话，或者用户创建失败但验证码已经被消费。

## 10.2 ACID

|特性|含义|项目中的体现|
|---|---|---|
|Atomicity 原子性|全部成功或全部失败|注册、改密、换绑|
|Consistency 一致性|满足数据约束|邮箱唯一、会话关联|
|Isolation 隔离性|控制并发事务相互影响|行锁、事务隔离|
|Durability 持久性|已提交变更持久保存|会话撤销、失败计数|

事务是保证数据一致性的基础，但不是业务规则正确性的自动证明。

开发者必须正确组织 SQL、加锁顺序、条件更新及提交时机。

## 10.3 SQLAlchemy 事务管理

常用写法：

```
with db.begin():
    repository.operation_one(db)
    repository.operation_two(db)
```

正常结束时提交事务。

异常发生时回滚尚未提交的操作。

Service 负责控制整体业务事务，Repository 只执行具体 SQL。

## 10.4 哪些失败也需要提交事务？

这是本次开发特别容易忽略的知识点。

|业务情况|处理|
|---|---|
|注册失败|回滚业务写入|
|Token 轮换失败|回滚轮换|
|邮箱换绑失败|回滚账号状态变更|
|密码输入错误|持久化失败次数|
|验证码输入错误|持久化 attempts|
|Refresh 重放|持久化会话撤销|

不是所有业务异常都意味着数据库事务应当全部回滚。

密码失败和验证码失败本身就是需要记录的安全事件。

当前代码在部分 `db.begin()` 作用域中先显式提交，再抛出异常。已有相关测试通过，但这种控制流需要保持清晰，确保提交之前没有不应持久化的其他业务写入。

未来可以在不降低事务一致性的前提下进一步整理提交和异常边界。

# 11. MySQL 行锁与并发控制

这是整套后端最值得学习的部分之一。

## 11.1 为什么普通 SELECT 不够？

例如两个请求同时读取一个尚未消费的验证码：

```
事务 A：查询验证码未消费
事务 B：查询验证码未消费

事务 A：校验成功
事务 B：校验成功

事务 A：执行登录
事务 B：执行登录
```

如果没有进一步的并发控制，同一个一次性验证码可能被重复使用。

## 11.2 SELECT FOR UPDATE

```
SELECT *
FROM users
WHERE id = :user_id
FOR UPDATE;
```

在事务中使用锁定读，可以阻止其他事务同时获取与该记录冲突的锁。

锁一般持续到事务提交或回滚。

它的本质不是锁住 Python 函数，而是由数据库协调不同事务对数据记录的竞争。

因此不同线程、不同后端进程也能够共享同一套锁机制。

需要注意：实际锁定范围取决于索引、查询条件和事务隔离级别。不能认为所有 `FOR UPDATE` 永远只锁定一条记录。

## 11.3 用户行锁为什么重要？

一个账号可能同时发生：

- 密码登录。
    
- 邮箱验证码登录。
    
- Token 刷新。
    
- 主动改密。
    
- 邮箱换绑。
    
- 远程撤销。
    
- 密码重置。
    

这些操作都可能影响账号安全状态。

所以对于已经存在的用户，我们使用 `users` 行锁作为重要认证写操作的统一入口。

```
锁定用户
    ↓
重新读取当前安全状态
    ↓
执行敏感业务
    ↓
提交事务
```

这样，同一个用户的重要认证写操作可以串行执行。

不同用户通常可以操作各自的数据，不必全部竞争同一个全局用户锁。

## 11.4 为什么采用统一加锁顺序？

核心认证路径采用：

```
users
    ↓
login_sessions
    ↓
refresh_tokens
```

对于已有用户的认证操作，先锁定用户，再锁定需要处理的 Session 和 Token。

原因之一是减少死锁。

错误示例：

```
事务 A：
持有 Session 锁
等待 User 锁

事务 B：
持有 User 锁
等待 Session 锁
```

A 等待 B，B 又等待 A，形成循环等待。

统一顺序后：

```
事务 A：获取 User 锁
事务 B：等待 User 锁

事务 A：继续获取 Session 和 Token 锁
事务 A：提交

事务 B：获得 User 锁
事务 B：重新检查业务状态
```

这里的等待是正常锁竞争，而不是上述循环死锁。

## 11.5 不同业务的实际锁定范围

|业务|主要锁定顺序|
|---|---|
|密码登录|User → 创建新 Session 和 Token|
|验证码登录|User → 验证码 → 创建 Session|
|注册|验证码 → 创建 User → 创建 Session|
|Token 刷新|User → Session → Token|
|当前退出|User → Session → 必要的 Token|
|主动改密|User → 当前 Session → 其他 Session/Token|
|邮箱换绑|User → 当前 Session → 验证码 → 批量撤销|
|密码重置|User → 验证码 → 批量撤销 Session/Token|

注册时尚不存在用户，不能先锁定已有用户行，因此依靠验证码行锁和数据库唯一约束保证一致性。

注意：不同业务还会取得验证码、索引、外键等相关锁，因此整个系统并非每条 SQL 都严格遵循完全相同的三表顺序。

统一用户行锁降低了主要认证竞态风险，但不能证明绝对不会出现死锁。

## 11.6 事务隔离级别

本项目需要关注 MySQL InnoDB 的 REPEATABLE READ（可重复读）行为。

普通 SELECT 通常属于一致性读，在同一个事务中可能沿用此前建立的快照。

SELECT FOR UPDATE 属于锁定读，读取并锁定当前可用版本。

一个危险情况是：

先通过普通查询建立旧快照，随后获得用户锁，再通过其他普通查询判断安全计数。

此时必须仔细确认是否可能使用旧快照数据。

因此新版 `get_current_user()` 使用独立的短生命周期数据库 Session，使认证查询不会提前开启后续业务 Service 使用的事务。

这既减少了事务边界冲突，也有助于控制安全查询的可见性。

# 12. MySQL 命名锁与跨进程限流

## 12.1 为什么还需要命名锁？

行锁适合保护已经存在的数据库记录。

但是某些操作不是针对某一条用户记录，例如：

- 全站邮件额度。
    
- 未注册邮箱的发码请求。
    
- 未知账号的登录尝试。
    
- 同一个 IP 的请求准入。
    
- 头像文件存储。
    
- 定时清理任务。
    

这些场景需要更灵活的跨进程互斥机制。

因此本项目引入 MySQL 命名锁。

## 12.2 核心 SQL

```
SELECT GET_LOCK(:name, :timeout);
```

释放：

```
SELECT RELEASE_LOCK(:name);
```

命名锁由名称标识，不要求数据库中存在一条对应业务记录。

## 12.3 命名锁和行锁的区别

|对比|行锁|命名锁|
|---|---|---|
|锁定对象|数据库记录及可能的索引范围|自定义锁名称|
|获取方式|SELECT FOR UPDATE 等|GET_LOCK|
|生命周期|数据库事务|数据库连接|
|COMMIT 后|释放相关事务锁|不自动释放|
|释放方式|提交或回滚|RELEASE_LOCK 或连接关闭|
|典型场景|改密、刷新、验证码消费|邮件额度、IP限流|

最重要的区别：

**命名锁属于数据库连接，而不是数据库事务。**

## 12.4 数据库连接池问题

SQLAlchemy 使用连接池复用数据库连接。

如果获得命名锁后，没有正确释放，就直接将物理连接归还连接池，后续请求可能受到残留锁的影响。

因此本项目的 `admission_session()` 需要：

1. 获取独立数据库连接。
    
2. 在该物理连接上调用 GET_LOCK。
    
3. 使用绑定到该连接的 Session 执行事务。
    
4. 在 finally 中回滚残留事务并释放命名锁。
    
5. 释放失败时使连接失效，避免带锁连接回到池中。
    

核心源码：

- `lock_repository.py`
    
- `rate_limit_service.py`
    

这也是本次开发的重要工程难点。

## 12.5 邮件额度的并发保护

错误实现：

```
请求 A 查询：还有1个邮件名额
请求 B 查询：还有1个邮件名额

A 发送
B 发送

结果：超出额度
```

正确设计：

```
获得 mail-quota 命名锁
        ↓
查询当日发送次数
        ↓
判断邮箱、IP及全站额度
        ↓
插入本次发送尝试
        ↓
提交事务
        ↓
释放命名锁
```

然后再执行实际邮件 HTTP 请求。

这使得 COUNT 与 INSERT 成为一个受到并发保护的准入过程。

## 12.6 为什么不直接用 threading.Lock？

`threading.Lock` 只能够协调同一个 Python 进程内的线程。

如果未来启动多个 Uvicorn Worker，各进程拥有不同的 Python 内存，普通线程锁不能保证跨进程互斥。

MySQL 命名锁由数据库统一管理，因此可以协调连接到同一 MySQL 实例的多个后端进程。

代价是锁竞争会占用数据库连接，需要控制等待时间和持锁时长。

它不是无限扩展的分布式锁方案，但适合本项目目前不引入 Redis 的架构选择。

# 13. 条件更新与数据库唯一约束

除了行锁和命名锁，我们还使用数据库条件更新作为最终状态保障。

## 13.1 验证码只能消费一次

核心 SQL 思想：

```
UPDATE email_verifications
SET consumed_at = :now
WHERE id = :verification_id
  AND consumed_at IS NULL
  AND invalidated_at IS NULL
  AND expires_at > :now
  AND attempts < :max_attempts
  AND send_status = 'SENT';
```

执行后检查：

```
result.rowcount
```

影响一行表示状态转换成功。

影响零行表示记录已经不符合更新条件。

因此不能仅仅根据此前 SELECT 的结果判断操作成功，必须检查最终 UPDATE 结果。

## 13.2 Refresh Token 条件轮换

同样采用条件更新：

只允许尚未撤销、尚未替换、尚未过期的 Token 被正常轮换。

第一次正常轮换影响一行。

第二次重复轮换不能再次成功。

## 13.3 邮箱唯一约束

业务层可以先查询邮箱是否存在。

但是两个用户可能在并发情况下同时查询到某个邮箱尚未被使用。

所以数据库唯一索引仍然是最终保障：

```
UNIQUE KEY uk_users_email (email)
```

当并发更新产生唯一约束冲突时，Service 捕获 IntegrityError，将对应冲突转换为 HTTP 409。

重要思想：

应用层检查负责友好的业务反馈。

数据库约束负责最终一致性。

两者不能互相替代。

# 14. 密码错误限制与认证事件

## 14.1 双层限流机制

第一层：IP 请求准入。

在执行较高成本的密码哈希计算之前，判断当前 IP 的请求次数是否超过限制。

第二层：用户密码失败限制。

同一个用户连续5次密码验证失败，暂时限制密码认证15分钟。

## 14.2 为什么不能只按照用户名计数？

同一个用户可以通过用户名或邮箱登录。

如果分别按照输入的用户名和邮箱计数，同一个账号就可能拥有两套失败次数。

因此对于已存在账号，失败计数以 `user_id` 为准。

## 14.3 认证事件模型

典型事件：

|事件|含义|
|---|---|
|PASSWORD_ATTEMPT|密码请求准入|
|EMAIL_CODE_ATTEMPT|验证码请求准入|
|PASSWORD_FAILED|密码验证失败|
|PASSWORD_LOCKED|账号密码认证进入锁定期|
|PASSWORD_CLEAR|失败计数重置|
|LOGIN_SUCCESS|登录成功|
|REGISTER_SUCCESS|注册成功|
|REFRESH_REPLAY|检测到重放|
|PASSWORD_CHANGE|主动改密|
|PASSWORD_RESET|重置密码|
|EMAIL_CHANGE|邮箱换绑|
|LOGOUT|当前退出|
|REMOTE_REVOKE|远程撤销|
|LOGOUT_ALL|全部退出|

`auth_events` 同时承担短期安全审计和限流计数的数据来源。

## 14.4 未知账号与模拟密码验证

对于不存在的账号，也执行一次模拟密码哈希验证。

目的是减少通过响应时间判断账号是否存在的可能性。

但模拟哈希只能缓解部分时间差异，不能完全消除账号枚举风险。锁定状态、验证码流程及不同业务响应仍需要独立审查。

# 15. 完整账号管理业务

## 15.1 注册

事务流程：

1. 验证注册验证码。
    
2. 检查密码规则。
    
3. 创建用户。
    
4. 消费验证码。
    
5. 创建 Session。
    
6. 签发双 Token。
    
7. 保存 Refresh 摘要。
    
8. 记录认证事件。
    
9. 提交事务。
    

注册成功直接登录，前端不需要再发起第二次登录请求。

## 15.2 密码登录

1. IP 准入检查。
    
2. 根据用户名或邮箱查找用户。
    
3. 获取用户行锁。
    
4. 检查密码锁定状态。
    
5. 验证密码。
    
6. 清除失败计数。
    
7. 创建 Session 与 Token。
    
8. 提交事务。
    

## 15.3 忘记密码

使用 RESET_PASSWORD 验证码证明邮箱控制权。

成功后：

- 更新密码摘要。
    
- 更新 password_updated_at。
    
- 撤销全部已有会话。
    
- 撤销对应 Refresh Token。
    
- 消费验证码。
    
- 记录安全事件。
    

不自动登录。

## 15.4 主动修改密码

使用当前有效会话和旧密码进行授权。

修改成功后保留当前会话，撤销其他会话。

## 15.5 邮箱换绑

要求：

- 当前有效 Session。
    
- 当前密码。
    
- 原邮箱验证码。
    
- 新邮箱验证码。
    
- 新邮箱满足唯一性约束。
    

全部成功后统一更新邮箱、消费两个验证码并撤销其他会话。

## 15.6 登录设备管理

根据 `login_sessions` 提供：

- 有效会话列表。
    
- 当前会话标记。
    
- 登录时间。
    
- 最近活跃时间。
    
- 根据 User-Agent 推断的设备名称。
    
- 撤销指定会话。
    
- 退出其他会话。
    
- 退出全部会话。
    

User-Agent 可以被修改，因此设备名称只用于展示，不作为安全身份凭证。

## 15.7 各安全操作的撤销范围

|操作|当前会话|其他会话|
|---|---|---|
|当前退出|撤销|保留|
|指定其他会话撤销|保留|仅撤销目标|
|修改密码|保留|全部撤销|
|邮箱换绑|保留|全部撤销|
|忘记密码|撤销|全部撤销|
|退出全部会话|撤销|全部撤销|

这些规则全部通过 `family_id` 和批量撤销机制实现。

# 16. Session 活跃时间管理

## 16.1 为什么需要两种 Session 期限？

空闲期限用于限制长期未使用的会话。

绝对期限用于限制一次登录能够持续存在的最长时间。

如果只设置空闲期限，频繁活动可能使会话无限续期。

如果只设置绝对期限，长时间不使用的会话仍然可能保持有效。

因此本项目同时采用7天空闲期限和30天绝对期限。

## 16.2 为什么不是每次请求都更新？

每次 HTTP 请求都写入 last_activity_at，会产生大量数据库写操作。

因此增加300秒写入节流。

满足以下条件才尝试更新：

- 已通过认证。
    
- 属于允许的主动业务请求。
    
- 请求成功。
    
- 带有约定的活动标记。
    
- 距离上次写入达到规定间隔。
    

后台轮询、会话探针、Token 刷新等操作不计入有效活动。

当前 SSE 路径也被排除，避免将流式连接的 HTTP 200 直接视为业务成功。

活动标记用于业务分类，不是证明真人操作的安全凭证。

## 16.3 为什么使用独立事务？

活跃时间更新不能直接提交原有学习业务使用的数据库 Session。

否则可能提前提交其他业务尚未完成的数据。

因此使用独立短事务更新活跃时间，并通过条件更新确保已撤销、已过期的 Session 不会被重新激活。

# 17. 头像处理与跨系统一致性

## 17.1 图片安全处理

头像支持 JPG、PNG、WebP。

默认限制：

- 文件大小不超过2 MiB。
    
- 解码像素数不超过1600万。
    
- 不接受动画图片。
    
- 最长边不超过512px。
    
- 统一转换为 WebP。
    
- 清除原始图片元数据。
    
- 使用服务器生成的 UUID 文件名。
    

不能仅信任客户端文件扩展名或 MIME 类型，必须实际解码并检查图片格式。

## 17.2 为什么不直接覆盖原头像文件？

因为数据库事务不能回滚文件系统操作。

假设先覆盖原头像，再更新数据库，而数据库提交失败，就无法自动恢复此前的文件内容。

因此正确顺序是：

```
校验并转换图片
        ↓
创建全新的 UUID 文件
        ↓
更新数据库 avatar_url
        ↓
提交事务
        ↓
确认没有引用后清理旧文件
```

如果数据库提交结果不确定，不急于删除新文件，而是交给后续孤儿文件清理任务判断。

## 17.3 暂存目录与原子移动

新头像先写入不公开的暂存目录。

写入完成后，通过同一文件系统内的原子移动发布完整文件。

这样可以减少浏览器访问尚未写完文件的情况。

## 17.4 孤儿头像

发生进程崩溃、提交结果不确定或旧文件删除失败时，可能留下没有数据库引用的头像。

清理任务检查：

- 文件是否符合系统命名规则。
    
- 是否仍被数据库引用。
    
- 是否已经超过安全宽限期。
    
- 是否为允许处理的普通文件。
    

上传、删除、孤儿清理使用相同的头像命名锁进行协调。

这是典型的跨系统一致性问题。

数据库和文件系统不存在本项目可直接使用的统一 ACID 事务，因此我们采用安全操作顺序、失败补偿和最终清理，而不是假设两者能够共同回滚。

## 17.5 部署边界

生产环境还需要：

- 持久化头像目录。
    
- 请求体大小限制。
    
- 上传频率限制。
    
- 并发图片解码资源控制。
    
- 静态文件访问安全检查。
    

当前头像文件处理代码尚待最终验收。

# 18. 定时清理与后台 Worker

## 18.1 为什么需要清理？

认证系统持续产生：

- 过期验证码。
    
- Refresh Token 历史记录。
    
- 已撤销 Session。
    
- 安全事件。
    
- 孤儿头像。
    

不清理会导致数据库和磁盘持续增长。

## 18.2 复用已有 APScheduler

原有 Worker：

`app/jobs/plan_expiration_worker.py`

原来每5分钟执行计划到期检查。

本次继续复用该进程，增加每小时一次的认证清理任务。

不新增 Celery、Redis 或独立消息队列。

## 18.3 清理策略

|数据|当前交付的清理策略|
|---|---|
|auth_events|默认保留30天，并覆盖实际安全计数窗口|
|email_verifications|超过保留窗口且至少已过期24小时|
|refresh_tokens|已过期超过30天|
|login_sessions|长期失效且不存在关联 Token|
|孤儿头像|无引用且超过24小时宽限期|

每张认证表每轮最多清理500条。

各表独立提交，以限制事务规模。

## 18.4 为什么不能立即删除旧 Refresh Token？

仍处于原始有效期的已轮换 Token，需要保留记录以支持重放检测。

如果立即删除，后端将无法根据 replaced_by 判断它是否是已经轮换的旧凭证。

因此清理策略必须服务于认证安全机制，而不是简单删除所有 revoked_at 非空的数据。

# 19. 统一异常处理与前后端契约

## 19.1 统一响应结构

```
{
  "code": 401,
  "message": "登录会话已撤销",
  "detail": {
    "code": "SESSION_REVOKED",
    "message": "登录会话已撤销"
  },
  "data": null
}
```

顶层 code 表示 HTTP 状态。

detail.code 表示具体业务原因。

## 19.2 为什么不能只根据401判断？

以下情况都可能返回401：

- Access Token 过期。
    
- Session 已被撤销。
    
- Refresh Token 无效。
    
- 登录密码错误。
    
- 敏感操作密码确认错误。
    

但前端处理策略完全不同。

|业务错误|前端处理原则|
|---|---|
|ACCESS_EXPIRED|协调自动刷新|
|SESSION_REVOKED|清除失效认证状态|
|SESSION_EXPIRED|要求重新登录|
|INVALID_CREDENTIALS|登录表单提示|
|INVALID_PASSWORD|密码确认提示，不误退出|
|RATE_LIMITED|显示限流反馈|

这也是后续 Axios 响应拦截器必须理解的后端契约。

## 19.3 敏感信息脱敏

Pydantic 的完整验证错误可能包含原始输入。

如果直接返回全部 exc.errors()，密码或验证码可能出现在错误响应中。

因此本项目只保留必要的：

- loc。
    
- type。
    
- 安全的 msg。
    

禁止回显真实密码、验证码、Refresh Token 和密钥。

# 25. 学习检查题与答辩准备

## 问题1：为什么已有 JWT 还需要 Session？

参考答案：

JWT 只能验证凭证签名、声明和有效期，无法独立实现实时撤销。Session 保存服务端的登录状态，从而允许远程撤销、改密后退出其他设备以及下一次请求立即拒绝旧 Access Token。

## 问题2：为什么 Refresh Token 每次使用都要轮换？

参考答案：

减少长期凭证重复使用的风险，并保留轮换历史，使后端能够识别有效期内已轮换 Token 的再次使用。

## 问题3：为什么重放检测必须先提交，再返回401？

参考答案：

如果直接在未提交事务中抛出异常，撤销 Session 的操作可能被回滚。必须先持久化撤销状态，再返回认证失败。

## 问题4：FOR UPDATE 锁的是 Python 线程吗？

参考答案：

不是。它由 MySQL 控制事务对数据库记录及相关索引范围的访问，因此可以协调不同线程和不同应用进程。

## 问题5：为什么统一按照 User、Session、Token 的顺序加锁？

参考答案：

将账号级安全操作统一协调，减少不同事务反向获取资源所产生的循环等待，并防止刷新、撤销和改密等业务发生状态冲突。

## 问题6：为什么有行锁还要使用命名锁？

参考答案：

行锁适合保护具体数据库记录，而邮件额度、IP准入和文件存储等操作不一定有对应的单条业务记录，因此使用命名锁协调跨进程临界区。

## 问题7：COMMIT 会释放命名锁吗？

参考答案：

不会。命名锁与物理数据库连接关联，必须显式释放，或者关闭对应数据库连接。

## 问题8：为什么邮箱唯一性需要数据库约束？

参考答案：

应用层提前查询存在并发竞态。数据库唯一索引才是防止两个用户占用同一邮箱的最终一致性保障。

## 问题9：为什么验证码校验和消费分成两个函数？

参考答案：

复杂业务可能需要多个条件全部满足后才允许消费，例如邮箱换绑需要两个验证码同时正确。将消费与业务写入放在同一个事务，可以避免验证码提前失效。

## 问题10：为什么邮件发送不放在数据库事务中？

参考答案：

外部 HTTP 请求可能耗时或失败，长时间持有数据库锁会影响系统并发能力。通过 PENDING 记录和后续发送状态更新实现跨系统协调。

## 问题11：头像更新能通过数据库事务自动回滚文件吗？

参考答案：

不能。数据库与文件系统具有不同的事务边界，因此需要新文件写入、数据库提交、旧文件清理以及失败补偿机制。

## 问题12：为什么不能把所有401都当成 Token 过期？

参考答案：

401 可能来自密码错误、会话撤销、凭证无效等不同原因。必须结合业务错误码判断是否刷新、提示错误或结束登录状态。

## 问题13：为什么 Repository 不能随意 commit？

参考答案：

Repository 只了解单条数据库操作，不知道整个业务是否成功。如果提前提交，Service 就无法将多个数据操作统一回滚。

## 问题14：为什么注册之后不再调用登录接口？

参考答案：

注册事务已经完成用户创建、验证码消费、Session 建立和双 Token 签发，因此重复登录会产生不必要的会话。

# 26. 本次后端开发总结

Auth V2.0 的核心价值不是增加了邮箱登录、头像管理或设备列表等页面功能，而是完成了账号认证系统的整体架构升级。

我们将：

- JWT 凭证验证。
    
- Session 生命周期管理。
    
- Token Rotation。
    
- 重放检测。
    
- MySQL 事务。
    
- 行锁。
    
- 命名锁。
    
- 条件更新。
    
- 安全限流。
    
- 外部邮件服务。
    
- 文件一致性。
    
- 统一错误契约。
    

结合到一个完整的业务系统中。

本次设计没有引入 Redis、Celery、复杂微服务或大型身份认证框架，而是利用当前 FastAPI、SQLAlchemy 和 MySQL 技术栈解决实际问题。

这种选择降低了当前项目的开发和部署复杂度，但仍然需要关注数据库锁竞争、连接池压力、外部服务失败及生产环境安全边界。

**真正需要掌握的不是某一条 SQL 或某一个 Python 函数，而是能够解释为什么这些机制需要同时存在，以及它们如何共同保证业务正确性。**
