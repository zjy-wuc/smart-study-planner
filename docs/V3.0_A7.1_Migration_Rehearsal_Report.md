### 1.5 历史数据清理范围

Auth V2 的 B 段会在单事务内**清空全部业务数据**（含 47 个用户及其计划/任务/记录/笔记等），仅保留 `ai_guard_mutex` 单行。这是不可逆操作，必须在正式执行前由开发者确认。预演库已完整复现该行为。

### 1.6 DDL 隐式提交风险

MySQL DDL 会隐式提交，脚本中的事务包裹**不能**保证失败后整体回滚。若在中途失败（如 `ALTER TABLE users` 已提交、后续 `CREATE TABLE` 失败），数据库会停留在部分迁移状态。因此：

- 脚本设计为“一次性执行”，任何失败都必须**从备份恢复后重跑**，不允许在半成品状态继续；
- 预演已完整走通，未出现中途失败。

### 1.7 重复执行风险

两份脚本均非幂等：重复执行会触发前置断言失败或对象已存在错误。恢复策略同样是“还原备份 → 重跑”，不得跳过断言。

### 1.8 迁移失败恢复流程

1. 立即停止应用与定时 Worker；
2. `mysqldump` 的迁移前备份已具备（见第 2 节），直接整库恢复；
3. 校验表数与关键行数；
4. 排查失败点，修复脚本后在隔离库重演，再重新进入正式流程。

## 4. 首个管理员初始化

### 4.1 方案

新增 `back/scripts/bootstrap_admin.py`，原则：

1. **复用现有注册流程**：调用 `auth_service.register()`，密码策略、PBKDF2 哈希、注册事件记录均由业务代码完成；
2. 本地隔离环境不发送邮件：按现有验证码机制生成 `REGISTER` 记录并标记 `SENT`，注册流程正常校验；
3. 注册成功后通过受控 SQL `UPDATE users SET role='ADMIN'` 授予角色；
4. 密码只从环境变量 `SSP_ADMIN_PASSWORD` 或标准输入读取，**不硬编码、不出现在命令行参数、不打印**；
5. 数据库守卫：默认仅允许 `ssp_v3_release_rehearsal` / `ssp_v3_demo`；正式库需 `--allow-production` 且额外设置 `SSP_CONFIRM_PRODUCTION_BOOTSTRAP=YES`；
6. 不开放任何公开管理员注册接口；用户名/邮箱已存在时拒绝覆盖。
