### 阶段 1：密码安全与 bcrypt

要讲清楚：

- 明文密码、编码、哈希、加密之间的区别。
- 为什么密码不能以明文保存。
- 哈希为什么通常不可逆。
- Salt（盐）的目的。
- 为什么同一个密码多次哈希可能产生不同结果。
- 注册时如何生成哈希并保存。
- 登录时如何验证用户输入的密码。
- bcrypt 的 72 字节输入限制及合理的边界处理。

计划实现的职责函数（具体命名可结合现有项目调整）：

```python
hash_password()
verify_password()
```

需要理解所用 bcrypt 库的哈希、生成 salt、验证接口。不要把明文密码写入数据库、日志或响应。

**阶段验收：** 用户能解释密码从注册请求到数据库保存的过程，并能独立完成哈希和验证测试。

### 阶段 2：JWT 原理与 Token 生成

要讲清楚：

- Token 解决什么问题，为什么登录后需要它。
- JWT 的 Header、Payload、Signature 三部分。
- Base64URL 编码不等于加密。
- Payload 不应放密码等敏感信息。
- `sub`、`exp` 等声明的用途。
- 签名如何帮助验证 Token 是否被篡改。
- Token 有效期和过期处理。
- 密钥应从环境变量/配置读取，不应硬编码或提交到 Git。

计划实现的职责函数（具体命名可结合现有项目调整）：

```python
create_access_token()
```

技术选择：计划使用 **PyJWT** 进行 JWT 的生成和验证；开始编码前核对依赖、版本和现有项目情况。密码哈希按课程要求使用 bcrypt。若库的 API 或兼容性发生变化，应以实际安装版本和官方文档为准。

**阶段验收：** 用户能解释 Token 的生成、签名、验证、过期以及为什么 Payload 不是机密信息。

### 阶段 3：后端认证架构与依赖注入

重点理解认证请求的职责分层：

```text
HTTP Request
    ↓
Router（接收请求、组织参数）
    ↓
Schema（验证输入和定义输出结构）
    ↓
Service（处理认证业务）
    ↓
Security（密码哈希 / Token 编解码）
    ↓
Database（查询用户）
    ↓
Response（返回结果）
```

解释并实践：

- Router 与 Service 为什么分开。
- Schema 与数据库表模型的区别。
- `security.py` 应承担什么职责。
- `Depends()` 的工作方式。
- `get_db()` 和认证依赖如何组合。
- `get_current_user()` 如何从请求中提取 Token、验证 Token 并查询用户。
- 为什么认证依赖可以复用于多个受保护接口。
- 为什么当前阶段优先使用 FastAPI 依赖注入保护路由，而不是为了“有中间件”而盲目增加全局 Middleware。

**阶段验收：** 用户能够画出后端认证调用链，解释每一层的职责，以及依赖注入如何获得数据库 Session 和当前用户。

### 阶段 4：后端注册、登录、Token 验证和接口保护

需要逐步实现或修复：

1. 注册：接收并验证用户数据，检查用户名是否重复，哈希密码，写入数据库。
2. 登录：根据用户名查询用户，验证密码。
3. 签发：登录成功后生成并返回 JWT Access Token。
4. 验证：从请求中读取 Bearer Token，验证签名、有效期和必要声明。
5. 当前用户：根据 Token 中可信的用户标识查询数据库用户。
6. 保护路由：在需要身份认证的接口上使用当前用户依赖。

必须考虑的异常：

- 用户名重复。
- 用户不存在。
- 密码错误。
- Token 缺失。
- Token 格式错误或签名无效。
- Token 过期。
- Token 中用户标识缺失或类型错误。
- Token 对应的用户已不存在。
- 数据库异常。

**授权与数据隔离是本阶段不可遗漏的内容：** 不能仅仅因为 Token 有效就允许访问任意用户的数据。查询、修改和删除学习计划、任务等资源时，应依据当前登录用户的身份进行所有权检查；不能信任前端随意传来的 `user_id`。

**阶段验收：** 后端能完成注册、登录、签发 Token、拒绝无效 Token、保护接口，并验证用户之间的数据隔离。

## 6. 技术约定与安全底线

- 后端：FastAPI + SQLAlchemy Session；保留用户已经掌握的 `text()` 原生 SQL 方式，除非有明确理由才调整。
- 密码：按课程任务使用 bcrypt，数据库只存哈希，不返回哈希给前端。
- JWT：计划使用 PyJWT；明确签名不是加密，Payload 不放秘密。
- 密钥：从环境变量读取；使用强随机密钥；不硬编码、不上传到 Git、不写进日志。
- 算法：验证 Token 时明确指定允许的算法，不接受 Token 自己声明的任意算法。
- 有效期：设置合理的 Access Token 过期时间，并测试过期行为。
- 错误信息：登录失败时避免泄露过多账号存在性信息；不要返回密码或密钥。
- HTTPS：生产环境使用 HTTPS；本地开发环境与部署环境要区分。
- CORS：精确允许实际前端 Origin，不使用不必要的宽泛配置；带凭证时必须正确处理 Origin 与 credentials 规则。
- 授权：后端每次访问用户私有资源时都要验证所有权，不信任客户端提供的用户 ID。
- 前端保护：只负责界面体验；最终安全边界始终是后端。
- Token 储存：讲清不同方案的安全权衡，不把 localStorage 作为无条件最佳实践。
- 依赖版本：安装或升级依赖前检查当前环境，避免不必要地升级整个项目。
